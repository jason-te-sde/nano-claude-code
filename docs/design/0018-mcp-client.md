# 0018: An MCP client over stdio, and what a server's tools have to pass

Status: accepted, implemented in `mcp/` (`jsonrpc.py`, `transport.py`, `client.py`, `tool.py`, `pins.py`, `result.py`, `servers.py`), in the session (`agent/session.py`, `cli/main.py`) and in `/mcp`.

A configured MCP server is a program that `ncc` starts, speaks to over its stdin and stdout, and takes tools from. Each tool it lists becomes a tool of the session under the name `mcp__<server>__<tool>`, the model can call it, and the answer comes back as one tool result. Everything else a server can offer (resources, prompts, sampling, elicitation) is not used, and the only transport is stdio. This note records why each part is as it is. What a server is allowed to do to a session is the whole question, and the answer is given by the checks listed here and not by trusting the server.

## Why

**The server is somebody else's program, and what it writes is somebody else's text.** Its tool list is read by the model and shown to the person; its results are read by the model; its failures are printed. So each thing it can write goes through a step of ours before it reaches a reader. The name of a tool is made into `mcp__<server>__<tool>` with every character outside letters, digits and underscores replaced, a name that two tools of a server come to is dropped from both, and so is one over 64 characters (`test_tools_that_come_to_one_name_are_all_dropped_and_the_warning_names_them`). A description has its terminal controls removed and is cut at 2,048 bytes on a character boundary. An input schema must be an object, at most 64 KiB and 32 levels deep, with no `$ref` that leaves the schema, since the specification forbids a client to fetch what a reference names. A tool that fails any of it is left out with a warning and is never registered quietly changed. A result is turned into text (an image or a resource becomes a line that says what was left out), cleaned of terminal controls, scrubbed of credentials, cut to `output_cap_bytes` with a note, and wrapped in `<mcp-result server=".." tool="..">`, with every `</mcp-result` inside it written `<\/mcp-result` so that nothing it says can end the wrapper early (`test_every_closing_tag_in_the_content_is_written_so_that_it_closes_nothing`). The system prompt tells the model that such results are third-party data and not instructions, in one sentence that is there only when a tool of a server is registered (`test_the_prompt_says_a_servers_results_are_data_only_when_an_mcp_tool_is_registered`).

**The person approves a definition, not a name.** A tool's fingerprint, a SHA-256 of its cleaned description and schema, is written down the first time it is seen, in `~/.nanoclaude/mcp-pins.json`. A tool whose fingerprint at a later start is not its pin is changed for the rest of that session, and a changed tool asks before every call, in every mode: the rule `mcp.changed` sits after every row that can refuse and before every row that can allow, so that no `allow` rule, no grant and not `bypass` lets it run unasked, and only a `deny` rule beats it (`test_a_changed_tool_is_never_allowed_in_any_mode_with_any_rule_or_grant`, `test_a_deny_rule_still_wins_over_a_changed_definition`). Answering "always" renews the pin for the next session and does not grant the tool for this one, and the confirmation says so. Under `-p` there is nobody to ask, so a changed tool is declined, and the line says that no rule will help. The tool list is read once, at the start, and a server's `list_changed` notification is ignored: the same reasoning forbids a description to change in the middle of a session, after the person has watched the tool do what it said.

**A tool of a server asks by default, and a rule names it exactly.** It is not read-only, so it falls to `default.ask`; `accept-edits` does not allow it; `bypass` does, as it allows everything the hard denials let through, and that is said in SECURITY.md. A rule is the whole registry name, `mcp__github__create_issue`, and `mcp__github__*` is refused, because a wildcard would also allow whatever a later version of the server adds. Such a call carries no path and no command, so the sandbox rows and the credentials rows of the policy have nothing to judge; the confirmation shows the server and the arguments the model wrote, cut at 1,000 characters, because those are what the person is being asked about.

**A server is started so that it can be ended.** The program is run directly, never through a shell, in the project root, as the leader of a process group of its own, with an environment of nine variables from `ncc`'s (`PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TMPDIR`, `TERM`) and what the server's `env` adds, so that no provider's API key reaches it unless the person wrote it there. Ending it closes its stdin and waits two seconds, sends SIGTERM to the group and waits two more, then SIGKILL, and it waits for the whole group to empty and not only for the process it started, so a worker the server forked is ended too. Its stderr goes to `~/.nanoclaude/logs/mcp-<name>.log`, newest megabyte kept, and not to the model.

**Two protocol eras, and the older one is the main path.** A client sends `server/discover` first. A result means the server speaks 2026-07-28 and every later request carries the version in `_meta`; -32022 is answered with a version both sides speak, or a failure; any other error, or five seconds of silence, means a server of the older kind, and the client sends `initialize` and `notifications/initialized` and accepts 2025-11-25, 2025-06-18 and 2025-03-26. Servers in use mostly speak the older protocol, so the fallback is tested at least as hard as the new path, and a server that answers neither is a failed server and not a hang. A line over 4 MiB is the server's failure. The client declares no capability, so a request from the server is answered `-32601`, except `ping`, and a result that asks for anything but completion (`input_required`) is a tool error.

**Starting and ending belong to the session, and a failure belongs to the server.** At the start of a session every enabled server is started at the same time, and `ncc` waits for all of them for at most fifteen seconds. A server that fails to start, or fails to say what its era is, or whose tools cannot be listed, or does not make it in time, is one warning line that names it and says why in a few words; its tools are not registered and the session goes on (`test_a_server_that_fails_adds_one_warning_and_registers_nothing_and_the_rest_start`). A pins file that cannot be read fails every enabled server closed, and none is started: a tool that cannot be compared with what the person last approved is not registered, and starting a server only to throw its tools away would be a process with no purpose (`test_a_corrupt_pins_file_fails_every_enabled_server_closed_and_starts_none`). The tools of all the servers are merged by one function before any is registered, and a name two servers come to is dropped from both with a warning and never raises, since the registry refuses a name twice (`test_a_name_two_servers_come_to_is_dropped_from_both_with_a_warning`). Every server is closed when the session ends, by `Session.aclose`, all at once: on a normal end, on an exception, on Ctrl+C, in the REPL and under `-p`, and `ncc` starts the servers after everything that could refuse the session, so that a missing key does not start a process, and ends them again if building the session fails after they were started (`test_the_servers_started_for_a_session_that_cannot_be_taken_up_are_ended`).

**The fifteen seconds include the time to end a server.** A start that is still going when its time is up is cancelled, and a cancelled start ends its server in the order above, which can take four seconds when the server ignores both its stdin and SIGTERM. So the wait for starts is not the whole budget: the last five seconds are kept for the closes, and a close still going when the budget ends is cut short with SIGKILL to the group, which cannot be ignored. The test uses a server that never answers and ignores everything, with the periods shortened, and fails if the whole takes longer than the budget (`test_the_budget_includes_the_time_a_cancelled_start_needs_to_close_its_server`, `test_a_close_that_does_not_finish_in_the_reserve_is_cut_short_with_a_kill`).

**A sub-agent is never given a tool of a server.** Its registry is built from the tool names of its persona, not taken from the session's, so a server added to the session cannot reach it (`test_a_sub_agent_never_sees_an_mcp_tool_the_session_has_registered`).

**What was left out.** The HTTP transports are not built: the specification has deprecated HTTP with server-sent events in favour of Streamable HTTP, a configuration that says `transport = "sse"` or `"http"` is refused with "not supported in this version", and `"http"` is the name kept for it. Resources, prompts, sampling, elicitation, roots and the task extension are not used, so the client declares no capability and is never asked for one. A tool list that changes during a session is not followed. `ncc` is a client only, and is not an MCP server.

## Costs

No real server is exercised anywhere in CI. The fake server (`tests/fixtures/fake_mcp_server.py`) is written from the design and speaks both eras as the design describes them, so what a server somebody else wrote does that the fake does not (a message written in pieces, fields the client does not read, a descendant that does something unforeseen) is untested. The older era is the one the wild uses, and the first run against a reference server is a manual one.

The session waits for its servers. A slow or silent server holds up the first prompt for up to fifteen seconds, and a legacy server that does not answer `server/discover` at all costs five seconds before the client tries `initialize`. Starting them together bounds the wait to the slowest and not the sum; starting them on first use would hide the wait inside a turn and would put the tools in the model's list too late to be used.

A server runs with the person's authority and is not contained. The sandbox and the credentials rules judge paths and commands, and a call to a tool of a server has neither, so they do not apply to it: the server can read and write whatever the person's account can, and the controls that remain are that it is asked about (unless the person allowed it), what it is given in its environment, and what comes back from it. A malicious server is not stopped by the pins either. A pin is trust on first sight: it catches a definition that changed after the person saw it, not one that was hostile when it was first seen, and the person sees a tool for the first time in the confirmation of its first call.

A server's credential is written in the configuration file, in the `env` of its table, as plain text, because that is how a stdio server is given one and no model-key style of naming a variable in the environment was built for it. `ncc` never narrows a configuration file that exists, so a file that is open to others shows them that credential, and the documents say to make it private.

A description cut at 2,048 bytes loses its tail, and a tool whose description is that long may lose what the model needed. A name that two servers come to costs both tools, including the one that was fine. A server that dies in the middle of a session is not restarted: `/mcp` shows it as failed, its tools stay registered, and a call to one is an error that says the connection is closed. A changed tool is asked about for every call of the session, which is tedious when it is used often and is the point. The confirmation shows at most 1,000 characters of the arguments and says how many more there are.

While one start writes its pins, nothing else on the event loop runs: the pins file is locked with a blocking call for up to five seconds when another `ncc` holds the lock, and a server's start waits behind it.

## Rejected alternatives

- A wildcard rule for a server, `mcp__github__*`. It is what a person writes first, and it allows each tool that a later version of the server brings, which the person has not seen. The rule names one tool, and a rule that is a wildcard is refused when the file is loaded.
- Pinning the server (its command, its version) instead of each tool's definition. What is read by the model is the description and the schema, and a server that keeps its version and changes a description is the case that matters.
- Letting `bypass` skip `mcp.changed` as it skips the questions. Bypass is a decision about prompts, made once at the start by someone who has not seen what a server will say tomorrow, and a definition that changed is exactly what it was not a decision about.
- Starting a server the first time one of its tools is called. A failure would surface in the middle of a turn, the model would not have had the tool in its list for the request that wanted it, and a server that takes ten seconds to start would stall that turn and not the start of the session.
- Refusing to start the session when a server fails. One optional server that is down would stop a person from working at all, and the person would learn to delete the configuration; a warning that names the server costs a line and loses only its tools.
- Passing the whole environment to a server, as a child process gets by default. A server would then hold every provider's API key, and a server needs `PATH` and `HOME` and few other things; what else it needs the person writes in its `env`, one name at a time.
- Following `list_changed`. It makes the list of tools, and the descriptions in it, different from the one the person saw at the start, at a moment nobody chose.
- Accepting `transport = "sse"` and treating it as the HTTP transport that will exist. A setting that is accepted and does nothing like what it says is the kind that this project refuses everywhere else, and a refusal costs one line.
