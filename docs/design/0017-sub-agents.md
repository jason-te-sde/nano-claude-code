# 0017: Sub-agents are nested sessions, and explore is the first

Status: accepted, implemented in `tools/task.py`, `subagents.py` and `agent/subagent.py`.

The `Task` tool takes an `agent` and a `prompt`, both required, and starts a sub-agent: a session nested in the one that called it, with an empty conversation, that returns one answer. In this version `agent` can only be `explore`, which has `Read`, `Glob` and `Grep`, is answered by the model of the `explore` role, and is told that it is read-only, answers only what it was asked and ends with a concise conclusion. Any other name is refused with the names there are. `/agents` lists them. The description the model reads is the one the design gives for the tool, word for word, and this note is the one that a change to a tool's description needs.

## Why

A sub-agent is an ordinary `Session`, not a branch in the loop. Three lines run between it and its parent and no others: its sandbox is made from the parent's and can only be narrower (`Sandbox.narrowed_to` refuses a root that the parent's does not contain), its cost goes up to the parent's ledger under its own role, and its final text comes back as one tool result while its conversation is neither added to the parent's nor stored. The loop, the executor, the policy and the router are the ones the person's own conversation uses, so a rule that holds for one holds for the other, and there is no second copy of any of them to drift. What differs is a handful of plain fields on `Session`: the role whose model answers it, a system prompt of its own, no `@` mentions, a gate that sees each request before it is sent, and the ids that mark its audit rows (`test_the_sub_agent_is_answered_by_the_explore_roles_model_and_not_the_main_one`, `test_the_parents_transcript_has_one_result_for_the_call_and_none_of_the_sub_agents_turns`).

What a sub-agent can touch is decided by building it, not by asking it. Its registry is made from the tool names its persona lists, so `explore` holds `Read`, `Glob` and `Grep` and there is no `Task`, no write tool and no MCP tool to take away; a tool added later is not in it until a persona names it, where a registry made by removing tools from the parent's would have it at once. Its policy is the parent's, so the mode and every `deny` rule hold, and its executor starts with the parent's session grants and cannot add one. Its front end answers every question with no and tells the person only that a request is under way: a question from inside a sub-agent would be about work the person cannot see, put at a moment they did not choose, so the call is declined and the sub-agent is told so, as headless mode does. The `Task` call itself is the question the person is asked, whether to spend the requests, and by default it asks, since it is neither read-only nor allowed without asking, and `allow = ["Task"]` in the person's own file lets it run (`test_the_sub_agent_has_read_glob_and_grep_and_nothing_else`, `test_a_sub_agents_sandbox_cannot_be_wider_than_its_parents`, `test_a_question_inside_a_sub_agent_is_declined_and_the_person_is_never_asked`, `test_the_sub_agent_inherits_the_session_grants_the_person_has_given`, `test_task_asks_by_default_and_a_rule_can_allow_it`).

A call that names no sub-agent is refused when it is judged, before anybody is asked, since a confirmation for a call that cannot succeed teaches a person to stop reading them. The refusal is a tool error that lists the names there are (`test_a_task_call_for_an_agent_that_does_not_exist_is_an_error_that_lists_explore`).

Three limits stop a sub-agent: 30 requests to its model, 200,000 estimated input tokens summed over those requests, estimated by the same counter the budget uses, and ten minutes of wall-clock time. The first two are a gate that the session calls with the estimate just before it sends a request, from the one place that sends the conversation's requests, so a retry after an overflow and a text-protocol reply asked for again count; a request that would go past a limit is never sent. The clock is a timeout around the whole run, because a gate between requests never sees a model that does not answer. Reaching a limit is not a failure: what comes back is the last text the sub-agent wrote, with a line that names the limit, since the work up to there is worth having. The person's own `max_turns` is not what stops it, so the nested session is given one turn more than its calls and the loop's limit never fires first (`test_a_sub_agent_is_stopped_after_thirty_model_calls_and_its_last_text_comes_back`, `test_a_sub_agent_is_stopped_before_it_goes_past_its_input_token_limit`, `test_a_sub_agent_whose_model_never_answers_is_stopped_at_the_wall_clock_limit`, `test_the_loops_own_turn_limit_is_not_what_stops_a_sub_agent`).

What comes back is the sub-agent's final text, stripped of terminal control sequences and scrubbed of credentials as any tool result is, and cut to `output_cap_bytes` with a note of how many bytes were cut; the key was validated from the start and read by nothing until this tool. Its tokens are priced at the model of its role and are a line of their own in `/cost`, and the router that keeps that ledger is the parent's, so the line is there as the money is spent and a sub-agent that is cancelled is still counted. Its tool calls are written to the audit table as the person's are, under the turn of the `Task` call and with that call's id in a nullable column, `parent_call_id`, added to a database from before it when the store opens (`test_the_sub_agents_cost_is_recorded_under_the_explore_role`, `test_an_answer_longer_than_the_output_cap_is_cut_with_a_note_of_how_much`, `test_the_sub_agents_calls_are_audited_under_the_task_calls_turn_and_id`).

## Costs

A sub-agent starts blind. It is not shown the project's instruction files or the project map, and it has no memory of the conversation, so a convention the person wrote down is not known to it and it may search for what the main model already has. That is the price of an empty conversation, which is what keeps what it reads out of the main one.

The limits are fixed and not measured. 30 requests, 200,000 estimated tokens and ten minutes come from the design and have not been tried against real tasks, so they may be too short for a large repository or too long for an expensive model. The token figure is an estimate at 3.5 characters a token, and the provider's count, which `/cost` shows, will differ. A stop that comes before the sub-agent has said anything returns a note that it said nothing and the line naming the limit. The timeout cancels a request or a search in flight.

The person is asked whether to spend the requests and is not shown what the sub-agent reads. Each read is held to the sandbox and the `deny` rules and is in the audit record, and nothing reads that record back in this version.

What comes back is a model's account of files, and it enters the main conversation as a tool result. A file that was written to steer a model can steer the answer, and the cap bounds the size of the answer and not what it says. The main model has to treat it as it treats the files.

A tool that asks cannot be given to a persona and used interactively: the question is declined, and the sub-agent stops. No built-in sub-agent has such a tool, since a read tool is never asked about, so this is a limit of the design that only a persona with a write tool would meet, and the tests meet it with one made for the purpose.

The nested session shares its id with the parent's, so the audit rows of the two are in one session and their call ids must differ. The ids that providers give do not repeat and the ones the adapters make are random, and a server that repeated one would make the audit refuse the second row.

A compaction inside a sub-agent is asked of the `compact` role and counts toward neither the call limit nor the token limit. With a model whose window is small that is possible, and it spends the `compact` role's money under that role.

How much routing `explore` to a cheaper model saves is not known. The main model decides whether to delegate, its own `Grep` and `Glob` calls stay on its own model, and a sub-agent that shares the main model's alias costs extra requests and saves nothing.

## Rejected alternatives

- A loop of its own for sub-agents, simpler than the session's. It would be a second executor, a second policy check and a second place to enforce the sandbox, and the first time the two disagreed a delegate would have more reach than the person's own session.
- A registry made by taking tools away from the parent's. A tool added to the parent later, an MCP tool for one, is in the sub-agent until somebody remembers to remove it. A list of names that a persona is given is the other way round.
- Letting the sub-agent ask the person, or ask through the parent. It interrupts at a moment nobody chose, about work the person cannot see, and an "always" answered there would be a grant made for a call the person never read.
- Stopping it with the loop's own turn limit. The limit is the person's setting for their conversation, it does not count a retried request, and it refuses the tool calls of the last turn where the sub-agent should simply stop.
- Checking the clock between requests instead of a timeout. A model that never answers is then never stopped, and a limit that cannot stop the one case that costs most is a comment.
- Folding the sub-agent's cost into the `main` role, or storing its conversation with the parent's. The first hides what routing `explore` does, which is the reason for the role, and the second puts into the conversation the detail that delegating was meant to keep out of it.
- Custom sub-agents from `~/.nanoclaude/agents/`, the `plan` and `general` sub-agents, and a depth of two, all of which the original plan has. Left out and not rejected: each gives a delegate more reach than `explore` has, a definition file needs a rule for the tools it may grant, and a delegate that starts delegates needs a limit on the cost of the whole tree, none of which `explore` needs.
